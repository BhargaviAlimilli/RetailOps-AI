# Technical Q&A grounded in the implementation

**Why React 19 and strict TypeScript?** Components model independently testable views and interactions. Strict types protect composition, while Zod validates untrusted runtime API responses; TypeScript alone cannot validate JSON. TanStack Query owns server state. Redux stores the cross-feature session in memory rather than duplicating the catalog or dashboard in a second cache.

**Why FastAPI?** Pydantic enforces API boundaries, dependencies centralize authentication/roles, and async endpoints fit PostgreSQL/provider I/O. Routes delegate transaction-heavy work to services. SQLAlchemy constructs parameterized statements; the model never writes executable SQL.

**How does streaming work?** The browser sends an authenticated POST using fetch and incrementally reads SSE. Explicit event names, request/message IDs and sequences distinguish deltas from terminal events. UTF-8 fragments and CRLF boundaries are decoded incrementally, duplicate events are ignored, and abort cancels the reader. Backend partial/terminal persistence and request-ID replay recover saved output without paying for another generation. A fresh retry uses a new request ID.

The upstream Gemini connection uses native incremental JSON streaming. An observed additive `serviceTier` field initially caused strict SDK parsing to discard valid tool calls; the adapter now ignores additive metadata while retaining strict application argument validation. A regression reproduces that wire response, and the real corrected turn, citations and saved replay pass. Sales tool results also label the UTC reporting dates so totals cannot be mistaken for a single day's revenue.

**How are conversations isolated and bounded?** Conversation ownership is checked against the authenticated user. Ordered messages and active-request leases are persisted. Short reservations and configured limits bound generations, concurrent work and history. Provider requests have deadlines and bounded retries; a retry cannot replay already emitted text. Session and document content are not placed in logs. Exact current limits live in Settings, not this document.

**How are model tools secured?** An allowlist maps names to Pydantic argument models and deterministic operations. UUIDs, dates, list sizes and quantities are checked. Tools return structured evidence from existing domain services; no arbitrary URL, SQL, Python execution, or model-generated code is accepted. The provider SDK's automatic function execution is disabled. The human workflow remains the only route to an authorized purchasing decision.

**How does RAG work?** The implementation accepts bounded text/Markdown, normalizes/chunks text, records ownership and ingestion status, obtains configured Gemini embeddings and persists pgvector vectors. Search is restricted to the caller's documents. Lexical and vector rankings can be combined through Reciprocal Rank Fusion and a deterministic reranking step. Returned citations refer to persisted document/chunk IDs and excerpts. Unsupported binary/PDF parsing is not claimed.

**Why hybrid retrieval?** Lexical matches preserve exact identifiers while vectors can match paraphrases. RRF combines ranked lists without assuming their scores share a scale. The implementation/evaluation must show actual outcomes; no claim that hybrid always wins, no invented recall figures, and no learned reranker claim follows from implementing the algorithm.

**Why LangGraph?** A bounded graph makes the replenishment steps and approval interrupt explicit, with PostgreSQL checkpoints for recovery. The workflow gathers sales/stock/supplier/policy evidence, creates an internal proposal, interrupts for an authenticated manager and applies a validated decision. It is a deterministic orchestration graph rather than a claim that an LLM autonomously manages purchasing. Each business mutation still goes through the transactional domain service.

**How is human approval enforced?** The API requires an authorized manager/admin action; conversational agreement is insufficient. Supplier associations, authoritative snapshotted costs, minimum quantities and packs are validated. Submission, decision and receiving are distinct transitions. Request-key and row locks prevent duplicate/competing execution. Audit records identify the actor and decision. No external supplier submission integration is claimed.

**How is financial correctness maintained?** PostgreSQL Numeric and Python Decimal handle prices, costs, totals and profit. Sales items snapshot unit cost/price so later catalog changes do not rewrite past gross profit. Inventory distinguishes on-hand/reserved/available quantities and records immutable movements. Tests cover rollback if one line of a multi-product receipt fails. JavaScript numeric conversion is only for chart/display formatting, not authoritative accounting.

**What is MCP used for?** A separate standard SDK stdio facade exposes four read-only tools over the existing authenticated HTTP API. It does not bypass document ownership or grant additional roles. Runtime tokens stay in protected environment configuration; redirects and external HTTP origins are rejected. The handshake test exercises actual protocol initialization/discovery without paid model calls.

**How is performance approached?** Reads are filtered/paginated on the server, query caching avoids duplicate view requests, and route-level lazy loading separates large chart/form features from sign-in. Queries use relevant foreign-key/time indexes. Context, document sizes, result counts and output lengths are bounded. Local build sizes and test timings do not constitute a production load benchmark. Capacity planning and measured load testing remain needed before sizing replicas.

**How is the system secured?** Passwords are hashed, bearer sessions are revocable and checked on the backend, analyst writes are forbidden, sensitive validation/provider/database errors are sanitized, and Markdown disallows raw HTML/executable links/automatic remote images. CORS/hosts are explicit; uploads and AI work have resource bounds. Bearer credentials in memory avoid automatically attached authentication cookies, while XSS prevention remains essential. A managed identity provider, distributed edge abuse protection and production operational review remain future deployment concerns.

**How are tests credible without paying for model calls?** Unit tests substitute the SDK/embedding provider and assert failure contracts, retries, cleanup and content handling. Integration tests use real PostgreSQL with migrated isolated schemas. Playwright exercises actual retail APIs with synthetic data. A real stdio MCP handshake is tested. These do not prove live model quality or provider availability; authorized live verification is a separate explicit milestone.

**How would this scale?** Stateless API replicas share PostgreSQL business data, leases, allowances and graph checkpoints. Cloud Run/Cloud SQL/Secret Manager templates prepare the deployment boundary without provisioning resources. Larger ingestion workloads need a durable background queue, document object storage/virus scanning where binary formats are added, measured vector-index/query tuning, distributed admission controls, observability and tested backup/rollback procedures. The current HTTP ingestion path and portfolio workload should not be represented as an operated enterprise-scale service.

**What remains unverified?** Consult the implementation progress log for actual tests and milestones. No deployed GCP environment, real paid-model output, retrieval-quality improvement, production performance or external supplier delivery should be claimed without specific recorded verification. Source code, a workflow definition and mocked tests each demonstrate different evidence; they are not substitutes for that live end-to-end proof.
